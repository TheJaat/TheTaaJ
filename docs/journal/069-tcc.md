# A C compiler on TheTaaJ

*Journal entry #69 · Era 6, step A. TCC, the Tiny C Compiler, now runs on TheTaaJ. It compiles a C file there, links it with TheTaaJ's C library, and writes a program that runs there. Getting there took three things underneath. The kernel now saves each thread's floating-point registers. The C library grew to what a compiler needs: setjmp, strtod, the calendar, getcwd, realpath, `%f` in printf. And libc.a shrank from 12.9 MB to about 200 KB, small enough to be one file on TaajFS. A boot test on both machines compiles three programs on TheTaaJ and runs them, then checks on the host that every file tcc wrote there is byte for byte what the same tcc writes on the host.*

```
taaj:/> tcc hello.c -o hello
[registry] shell gave tcc: files
[init] started tcc for the shell, from a file
[process] 41 "tcc" exited with code 0
taaj:/> hello
hello from tcc: 6 * 7 = 42, 1/8 = 0.125
taaj:/> tcc bad.c
bad.c:3: error: 'nothing' undeclared
tcc exited with code 1
```

## Why

Era 6's goal is to build TheTaaJ's software on TheTaaJ. Until now every program on the disk was compiled somewhere else, by clang on the host, and copied over. A system that cannot compile is a system you can only use. The way to the goal is in three steps:

- **A (this entry):** a C compiler that runs on TheTaaJ and turns a C file there into a program that runs there.
- **B:** that compiler builds TheTaaJ's own C programs and C library on TheTaaJ, and a program written in `edit` is built and run without leaving the system.
- **C:** the compiler compiles itself on TheTaaJ.

I chose TCC because it is a compiler, an assembler and a linker in one C program of about 100,000 lines. It needs nothing but a C library. Clang and GCC are each millions of lines of C++ and need a C++ library that TheTaaJ does not have. They are for later.

## The picture

```
  on the host                                   on TheTaaJ
  ───────────                                   ──────────
  ports/tcc  ──cc──▶  cross/taaj-tcc  ──┐       /tcc            the compiler
       │                                ├──▶    /lib/tcc/        tcc's headers, libtcc1.a
       └──clang + libc.a──▶  tcc ───────┘       /include/        the C library's headers
                                                /lib/libc.a      the C library
  libc/ (Rust + C) ──▶ libc.a ─────────────▶

  tcc hello.c -o hello:  read hello.c, /include/stdio.h, /lib/tcc/include/stddef.h ...
                         compile ─▶ link with /lib/libc.a and /lib/tcc/libtcc1.a ─▶ write hello
```

`tools/build-tcc.sh` builds two compilers for each CPU from the same source:

- **a cross compiler**, `taaj-tcc`, which runs on the host and writes TheTaaJ programs;
- **tcc itself**, compiled by clang and linked with TheTaaJ's libc.a, which runs on TheTaaJ.

The cross compiler also builds `libtcc1.a`, TCC's small library of helpers that the code it generates calls. `tools/put-tcc.sh` puts everything on a disk where tcc looks for it.

## Floating point in the kernel: every thread its own registers

A C compiler does floating-point arithmetic, so the first thing TCC needs from TheTaaJ is working floating point.

The kernel is built for "soft-float" targets: it never touches the FPU, the SSE registers (PC) or the vector registers (AArch64). Until now user programs didn't either: C was compiled with `-mgeneral-regs-only`. But a program that uses those registers expects them to keep their values across a thread switch. The kernel's switch saved only the general registers, so one thread's floating-point values leaked into the next. So:

- **PC:** `switch_context` now also does `fxsave64`. That one instruction writes the x87 FPU, the sixteen XMM registers and MXCSR as a 512-byte block below the six saved registers. `fxrstor64` loads the next thread's block. `enable_fpu()` turns the FPU and SSE on at boot: CR0.EM off, TS off, MP and NE on, CR4.OSFXSR and OSXMMEXCPT on. A new thread's block holds the state after a reset: control word 0x037F, MXCSR 0x1F80, every exception masked.
- **AArch64:** the frame grows from 96 bytes to 624: v0 to v31 (`stp q`, two at a time) plus FPCR and FPSR. `enable_fpu()` sets CPACR_EL1.FPEN so FP instructions no longer trap. The assembly says `.arch_extension fp`, because the kernel's target has no FP instructions and these lines are the only ones that use them.

I chose eager saving: every switch saves and loads. The other way is lazy switching, which traps on a thread's first FP instruction and saves only then. It does less work, but it is trickier with several CPUs, and 512 bytes per switch is cheap next to what a switch already costs.

The test is `cfloat`. It keeps running sums in `double` and `long double` and checks them every round against the same sums in integers. The values stay below 2^53, where every whole number is exact, so any difference is a fault, not rounding. Four copies run at once with different seeds.

## The C library grows

What TCC's source calls that the library did not have:

| Function | How |
|---|---|
| `strtod`, `strtof`, `strtold`, `atof` | Rust's `core` parses the number, correctly rounded, with no system needed. The answer crosses to C as integer bits (see below) |
| `setjmp`, `longjmp` | a few lines of assembly per CPU: the callee-saved registers, the stack pointer and the return address; on AArch64 also d8 to d15 |
| `time`, `gettimeofday`, `gmtime`, `localtime` | seconds since boot (there is no clock driver that knows the date yet), turned into a calendar date by Howard Hinnant's civil-from-days method |
| `getcwd`, `realpath` | the working directory a program is given; `realpath` asks the file service whether the path exists, then works out `.` and `..` |
| `fdopen`, `assert`, `abort` | a stream on a descriptor; assert prints `file:line: function: assertion failed: expr`, and abort exits with code 134 |
| `ldexp`, `ldexpl`, `fabs` | scaling in steps that each fit; fabs clears the sign bit |
| `strtoll`, `strtoull`, `strpbrk` | small additions |
| `getenv`, `execvp` | honest failures: no environment (NULL), and no replacing a program (ENOSYS, a new errno) |
| headers | `stdint.h`, `limits.h`, `inttypes.h`, `math.h`, `setjmp.h`, `time.h`, `sys/time.h`, `assert.h`, all TheTaaJ's own now, so TCC (which has none of clang's headers) can use them |

### Two kinds of floating point, and why the bits cross as integers

The C library is half Rust and half C. The Rust half is built for the soft-float target, like the kernel. A Rust function returning an `f64` puts it in a general register. A C caller built with floating point looks for it in XMM0 (PC) or v0 (AArch64). They would never meet, and the linker cannot tell, because a symbol has no "calling convention" written on it. So `__taaj_parse_double` returns the double's bits as a `u64`, which both conventions return in the same register, and C turns them back with `memcpy`.

The same trap was waiting in Rust's support library. On AArch64 a `long double` is 128 bits, and the CPU has no instructions for it, so a compiler calls helpers such as `__addtf3` for each operation. Rust's compiler_builtins has them, built soft-float: they read their arguments from general registers. Clang's code passes them in q registers. Nine of clib's checks failed this way. The fix has two halves:

- **C versions:** the helpers now come from C: `libc/c/fp128.c`, a copy of TCC's own `lib-arm64.c`, compiled with floating point.
- **Rust's hidden:** Rust's helpers are made local in libc.a with `llvm-objcopy --localize-symbol`, invisible to the linker (`LIBC_RUST_PRIVATE` in the Makefile).

### printf learns `%f`, `%e` and `%g`

TCC's first boot printed `1/8 = %.3f`: the library's printf had no floating point. Doing it right is not obvious. `printf("%.2f", 0.125)` must give `0.12`: 0.125 is exactly halfway, and ties go to the even digit. But 0.15 is really 0.1499999999999999944…, so it gives `0.1`. You can only round right if you know every digit of the exact value.

The idea is simple. Every double is a whole number m (up to 53 bits) times 2^e:

- **e ≥ 0:** the value is m doubled e times;
- **e < 0:** the value is m / 2^-e, which is m × 5^-e with the decimal point -e places from the right, because 1/2 = 5/10.

So the exact digits come from multiplying by 2 or by 5 over and over, in an integer stored as 32-bit "limbs" of nine decimal digits each. The longest case, the smallest subnormal, has 767 digits. Rounding on exact digits is then just "a 5 followed by only zeros is a tie". It is written in C, not Rust, so that `make libc-test` can still compile format.c on the host and compare it with glibc. 2127 formats agree, including 1000 random doubles from the whole range, each printed six ways.

### The archive: 12.9 MB to 208 KB

libc.a is the Rust half (Rust's archive includes `core` and `compiler_builtins`) plus the C objects. Built as before, it was 12.9 MB. A file on TaajFS can hold about 4 MB, and tcc reads the whole archive every time it links. Four cuts:

1. **link-time optimisation** (`lto = true`): the Rust half becomes one object containing only what is used;
2. **`--strip-debug`**;
3. **removing `.llvmbc` and `.llvmcmd`**, the LLVM bitcode that Rust embeds in every object for a link-time optimiser that no linker here uses;
4. **`tools/thin-archive.py`**: of compiler_builtins' 400-odd members, keep only those that something kept needs, and then whatever those need, until nothing changes (plus `memcpy` and its relatives, which a compiler may call unasked).

The result: 29 of 435 members, 208,276 bytes on the PC and 239,344 on AArch64.

## TCC for TheTaaJ

`ports/tcc` is upstream TCC (repo.or.cz, commit `84fdcd9`, version 0.9.28rc), copied in unchanged in its own commit. TheTaaJ's changes are a second commit on top, so `git diff` between them is everything TheTaaJ changed. `ports/tcc/UPSTREAM` says where it came from, and it stays under TCC's licence, the LGPL 2.1. The changes are a new target OS, `TARGETOS_TheTaaJ`:

- **no crt files:** libc.a has `_start`, so there is no crt1.o, crti.o or crtn.o to add;
- **static only:** no shared libraries, so `-static` is always on and there is no ELF interpreter;
- **`__TAAJ__` instead of `__linux__` and `__unix__`:** a program that `#ifdef`s on Linux must not believe it can make Linux system calls. tccdefs.h treats `__TAAJ__` like Linux where it only means "an LP64 ELF system" (`int64_t` is `long`);
- **the paths:** tcc's headers and libtcc1.a in `/lib/tcc`, the C library's headers in `/include`, libc.a in `/lib`. The cross compiler sets the host's paths in its own config.h;
- **no `-run`:** TCC can compile into memory and jump there, but that needs memory that is written and then executed, and TheTaaJ's W^X rule gives programs none;
- **an upstream bug, fixed:** TCC reuses bit 31 of a section's flags as its private "SHF_PRIVATE" mark. That is the same bit as ELF's `SHF_EXCLUDE`, which Rust's `.llvmbc` sections carry. Such a section, once loaded, became one of tcc's private sections, which have no number, so every symbol in it looked undefined. On AArch64 those are the `$d` mapping symbols, hence 38 errors of `unresolved reference to '$d'`. tcc now skips `SHF_EXCLUDE` sections, as ELF says a linker should.

The shell gives `tcc` the files service by name (`CHANGE_PROGRAMS`), as it does `cp` and `mv`, because a compiler reads sources and writes programs.

The x86-64 and AArch64 cross compilers write programs the loader accepts as they are. The text starts at 0x400000, and the read-only, executable and writable segments are on separate pages, which the loader's W^X check requires.

## Design decisions

| Decision | Chosen | Rejected, and why |
|---|---|---|
| The compiler | TCC: compiler, assembler and linker in one C program | Clang or GCC: millions of lines of C++ and a C++ library first. chibicc or cproc: smaller, but they need a separate assembler and linker |
| Where TCC lives | `ports/tcc` in TheTaaJ: upstream at a pinned commit, TheTaaJ's changes as commits on top | A git submodule: one more repository, and the changes in another place. Patches applied at build time: the changes out of sight |
| What TCC calls the system | A new target OS, `__TAAJ__` | Pretending to be Linux: programs would `#ifdef` their way into Linux system calls |
| Saving FP registers | Every switch, eagerly | Lazily, trapping on first use: less work, harder with several CPUs. `xsave` with AVX state: nothing uses AVX yet |
| strtod | Rust's `core`, bits returned as an integer | My own: correct rounding needs arbitrary-precision arithmetic, and `core` already has it right |
| printf's floating point | Exact digits by multiplying by 2 or 5, in C | Multiplying by 10 in a double: the last digits come out wrong. In Rust: the host comparison builds only the C file, and Rust's `{:e}` is not C's `%e` |
| AArch64 long double | 128-bit, helpers from TCC's `lib-arm64.c` | `-mlong-double-64`: clang does not have it for AArch64, and it would break the ABI |
| The archive's size | LTO, strip, no bitcode, keep only what is reachable | The whole archive: 12.9 MB, three times what one file may hold |
| Checking tcc's output | Byte for byte against the cross compiler's, from the same sources | Only running the programs: a wrong byte in a part no test runs would go unnoticed |
| `-run` | Not on TheTaaJ | Memory both writable and executable for one program: a hole in W^X |
| Who builds the tcc that runs on TheTaaJ | Clang, for now | The cross TCC: that is step C, TCC building itself |

## Bugs

- **Floating point leaked between threads.** This is the reason for the kernel change, not a bug found afterwards. But the test for it was too weak at first: with 3,000,000 rounds per copy, each finished in a few time slices, so the four barely overlapped. At 30,000,000 they run side by side for several seconds.
- **I thought the AArch64 test missed the mutation.** It didn't. `make aarch64-keys-test` does not rebuild the kernel, so I had been booting the old one. After `make kernel-aarch64`, the mutant gave 13 to 23 million wrong rounds out of 30 million.
- **Nine long-double checks failed on AArch64.** This was the soft-float/hard-float mismatch in Rust's `__addtf3` and its relatives, described above. The linker was happy, because nothing in an object file says which registers a function reads its arguments from.
- **libc.a was 12.9 MB.** That is more than three times what a TaajFS file can hold. See "The archive".
- **`1/8 = %.3f`.** TCC's first program on TheTaaJ ran perfectly, and printf had no `%f`.
- **`unresolved reference to '$d'`**, 38 times, on AArch64 only: TCC's SHF_PRIVATE / SHF_EXCLUDE clash, described above. The PC never hit it: its objects have no symbols in those sections.
- **The test's comparison ran in the wrong directory.** It changed into the work directory and then called the cross compiler by a relative path. Everything on TheTaaJ had passed; the host half failed with "not found".

## How I checked it

Automated, on the host (`make libc-test`):
- format: 2127 formats against glibc's printf, about 1,950 of them new: ties, -0.0, infinities and NaN, the largest and smallest doubles, `%.1074f`, widths and flags, and 1000 random doubles;
- number: the 3 new Rust tests of strtod's helpers (how far a number goes, and when it is out of range), now part of `make libc-test`;
- string: the new `strpbrk` test.

Automated, by booting (in `make test64`):
- `boot64-test` and `aarch64-keys-test`:
  - `clib` runs 53 checks of the new library parts: setjmp and longjmp through 20 calls with doubles kept in callee-saved registers, strtod's hard cases (0.1, a tie, the largest subnormal, overflow and underflow with ERANGE), ldexp at the edges, the library's own fabs, printf's floating point, the calendar on 29 February 2000 and the last second of 2099, getcwd, realpath with `..`, fdopen, getenv and execvp.
  - `clib assert` prints `libc/programs/clib.c:212: main: assertion failed: number == 2` and exits with 134.
  - Four `cfloat` copies run 30,000,000 rounds each, with 0 wrong.
- `tcc64-test` and `aarch64-tcc-test`, new. A disk with tcc and its trees, and on TheTaaJ:
  - `tcc hello.c -o hello`, then `hello`;
  - `tcc chello.c -o chello2`, then `chello2 one two`;
  - `tcc -c clib.c`, then `tcc clib.o -o clib2`, then `with files clib2`: 53 checks passed, in code TCC wrote;
  - `tcc bad.c`: the error on line 3, exit code 1.
  
  Then, on the host, the cross compiler builds the same files from the same sources. `hello`, `chello2`, `clib.o` and `clib2` copied off the disk are identical to them, byte for byte, on both machines.

Mutation experiments, 6, all caught:
- K1, the PC switch without `fxsave64`/`fxrstor64`: the four cfloat copies were 14.8 to 19.6 million rounds wrong out of 30 million (`boot64-test`).
- K2, the AArch64 switch without the q registers: 13.7 to 23.4 million wrong (`aarch64-keys-test`, once the kernel was rebuilt).
- L1, printf rounding ties up instead of to even: 2 of 2127 formats differ from glibc's.
- L2, fabsl clearing a bit in the wrong byte: clib, compiled by tcc on TheTaaJ, failed "the library's fabsf and fabsl" (`tcc64-test`).
- S1, the shell not giving tcc the files: `tcc: error: file 'hello.c' not found` (`tcc64-test`).
- T1, TCC without the SHF_EXCLUDE fix, linking against an AArch64 libc.a that still has its bitcode: 32 `unresolved reference to '$d'`. With the fix, the same link works. This one is by hand, on the host: the libc.a the tests use no longer has those sections, so no test would catch it.

Clippy is clean everywhere.

The testing note's steps were run as scripted boots on scratch disks.

Not tested:
- A person typing. Every key was sent by the boot scripts.
- How long tcc takes on TheTaaJ, beyond "well within the test's ninety seconds a step".
- `%Lf` with a long double that is not also a double: it is printed via the nearest double, by design.
- Programs larger than clib: TCC compiling TheTaaJ's own programs on TheTaaJ is step B.

## What is still missing

- Step B: TheTaaJ's C programs and C library built by tcc on TheTaaJ, and `edit` then `tcc` then run, all without leaving the system.
- Step C: tcc compiling itself.
- `-run`, shared libraries, debug information and a debugger.
- The date: `time()` counts from boot until there is a real-time clock driver.
- `%a` in printf; `%Lf` with all of the PC's 80 bits.
- Programs from tcc are larger than clang's (124 KB for hello against 54 KB for chello). TCC has no `--gc-sections`, so it links the whole Rust half of the library, which is one object since LTO.

## What I learned

- Floating-point registers are part of a thread, as much as the stack pointer is. A kernel that never uses them still has to save them, because its programs do.
- Two halves of one library can disagree about where a number lives, and nothing catches it until the numbers are wrong. A symbol in an object file has a name and an address, but no calling convention.
- Printing a double exactly needs only multiplication, by 2 or by 5. Once every digit is known, rounding to even is a comparison.
- A flag bit that a program borrows for its own use is a bug waiting for an input that has that bit set. TCC's SHF_PRIVATE waited until objects carrying SHF_EXCLUDE came along.
- A compiler gives you a strong test: compile the same source with the same compiler in two places and compare the bytes. Any difference in the files tcc read, in the library's I/O or in the arithmetic would show.
